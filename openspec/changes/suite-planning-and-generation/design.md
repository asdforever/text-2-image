## Context

参见 `proposal.md` 的动机。当前 `SuiteWorkspace` 在浏览器内拼接模块规划，规划与进度保存在 Zustand，生图调用 `mockGenerateSuite`；FastAPI 只实现了项目素材、生成配置以及主图的真实生成链路。阶段 3B 已提供持久化 `generation_batches`、`generation_module_tasks`、`generation_image_slots`、`generation_slot_attempts`、Worker 租约、取消与单槽位重试，但其编译服务、单源图请求和领取顺序仍以主图为中心。

详情图允许 1–4 张产品源图、1–5 个模块、每模块 1–4 张。系统当前按单用户运行，但所有新记录和服务继续携带 `workspace_id`，写操作保留幂等边界。真实图片 Provider 只能在用户确认后由 Worker 调用，自动化测试不得产生计费请求。

## Goals / Non-Goals

**Goals:**

- 建立独立于浏览器生命周期的详情页规划聚合，支持多模态编译、模块独立编辑、排序、确认和恢复。
- 让一次确认同时冻结规划与各模块实时任务提示词，并原子创建可执行套图批次。
- 复用阶段 3B 的槽位、尝试、取消、重试、租约和资产发布逻辑，只扩展批次来源、多源图和模块顺序。
- 在数据库领取语句中落实模块间串行，同一模块的槽位仍可按 Worker 并发容量并行。
- 保持主图现有 API 和执行语义兼容。

**Non-Goals:**

- 不实现阶段 5 的画布、节点位置、当前/最终版本选择和多人并发协作界面。
- 不实现阶段 6 的 OCR、局部重绘或图片编辑会话。
- 不建立新的向量检索产品；阶段 4 只解析并冻结已有或通过端口提供的版本化参考片段。
- 不在自动化测试或规划编译阶段调用真实计费图片 Provider。

## Decisions

### 1. 用“规划 + 模块”建立独立持久化聚合

新增 `suite_plans` 和 `suite_plan_modules`。规划保存项目、工作区、状态、修订号、源图列表快照、配置/约束/参考资料快照、编译与确认幂等信息以及关联批次；模块保存稳定模块键、连续位置、生成数量、标题、文案摘要、画面说明、补充参数、编译输出、当前实时任务提示词和模块修订号。

规划状态采用 `compiling`、`awaiting_confirmation`、`confirmed`、`failed`。编译时先创建 `compiling` 记录，使失败可追踪；所有模块完成后转为 `awaiting_confirmation`。确认在一个数据库事务内冻结规划并创建批次，失败时两者都不生效。

备选方案是把整个规划放入 `generation_batches.snapshot`。该方案无法在确认前自然支持模块级修订、排序和乐观并发，也会把“内容规划”与“图片执行”两个生命周期耦合，因此不采用。

### 2. 规划编译器返回结构化模块结果

新增详情页规划编译端口，输入包括 1–4 张图片、已发布配置解析结果、模块目录、补充参数和已解析参考片段；输出是与请求模块键一一对应的结构化结果。服务端验证键集合、顺序、数量和字符串长度，不接受模型返回的新模块、虚构配置或越界数量。

市场、风格和真实性约束继续通过共享约束解析器取得，并作为只读卡片与模块任务提示词分开保存。模块绑定提示词存在时解析到具体已发布版本；缺失可选绑定时使用带稳定版本号和内容哈希的内置规划基线。最终图片提示词仍由固定顺序的只读约束卡与用户确认后的模块任务提示词确定，编译模型不负责改写全局卡。

备选方案是先生成整页自由文本，再由第二次模型调用拆模块。它会增加成本并让模块顺序、数量和事实边界更难验证，因此采用一次结构化规划编译并对每个模块保存独立输出。

### 3. 参考资料通过解析端口按版本冻结

规划请求只提交参考标识和版本。`PlanningReferenceResolver` 在当前工作区解析版本化片段，返回标题、来源、内容哈希和允许进入模型的字段摘要；服务把这些信息复制到规划快照。没有参考选择时返回空集合。

这为现有测试夹具和后续正式 RAG/资源库保留稳定接口边界，同时避免信任客户端提交的任意“快照内容”。若当前部署没有参考资料提供器，空选择仍可用；提交非空引用则返回明确的不可用或不存在错误，而不是静默忽略。

### 4. 模块编辑使用双层乐观修订

模块内容修改请求携带 `expectedPlanRevision` 和 `expectedModuleRevision`；排序请求携带 `expectedPlanRevision` 与完整模块 ID 顺序。成功后规划修订加一，受影响模块修订加一。数据库更新条件包含旧修订号，影响行数为零时返回 409 和当前修订摘要。

确认请求携带 `expectedPlanRevision`，只允许最新 `awaiting_confirmation` 规划确认。确认后所有编辑端点返回状态冲突。此设计比最后写入覆盖更适合刷新恢复，也为阶段 5 的更完整协作状态保留边界，但本阶段不做实时协同或字段级合并。

### 5. 一次规划确认直接创建已排队批次

确认页面同时展示结构规划、每模块任务提示词、事实/无法确认项和只读约束卡。用户的确认请求包含最新规划修订及每模块最终可编辑字段；服务验证后直接创建 `queued` 套图批次与槽位，不再要求第二次批次提示词确认。

现有主图继续使用“批次编译 -> 批次确认”。套图复用批次仓储的新增 `create_confirmed_from_plan` 边界，把已编译模块快照转换为模块任务、最终提示词与槽位。这样既保留统一执行基础设施，也避免对同一套图进行两次语义相同的人工确认。

### 6. 扩展批次来源、多源图与显式模块位置

`generation_batches` 增加 `kind`（`hero`/`suite`）和可空 `source_plan_id`；保留 `source_asset_id` 作为兼容主图及套图主源图，完整 `sourceAssetIds` 及对象哈希保存在冻结快照。`generation_module_tasks` 增加 `position`，并以 `(batch_id, position)` 保证连续唯一顺序；现有主图批次按请求顺序写入位置。

图片执行端口由单图片请求扩展为有序图片输入列表，同时保留单图片便利构造，避免破坏主图调用者。Worker 从批次快照解析并逐一验证对象归属、状态、媒体类型和哈希，再把全部图片交给支持多图的 Provider 适配器。Provider 不支持多图时必须在确认或执行前返回明确能力错误，不得静默只取第一张。

### 7. 在仓储领取条件中实现顺序资格

PostgreSQL 领取查询只选择 `queued` 槽位，并排除同一批次中任何位置更小且状态不属于 `succeeded`、`failed`、`cancelled`、`needs_retry` 的槽位。随后仍使用 `FOR UPDATE SKIP LOCKED` 领取同一合格模块的多个槽位。内存仓储实现同样的资格函数，确保单元测试和生产语义一致。

批次内前序模块失败不会永久阻塞后续内容；失败和 `needs_retry` 被视为本轮终态。若用户重试前序槽位，该槽位重新成为非终态，尚未领取的后续槽位会再次被资格条件阻塞；已经 `leased` 或 `dispatching` 的后续调用不会被强制中断。

备选方案是在确认时只创建第一个模块槽位，完成后再动态创建下一批槽位。该方案使槽位总数和确认快照不稳定，也增加崩溃恢复的补偿逻辑，因此所有槽位一次创建，通过领取资格控制执行。

### 8. 项目范围 API 与前端恢复

新增以下 API 边界：

- `POST /api/projects/{projectId}/suite-plans/compile`
- `GET /api/projects/{projectId}/suite-plans/latest`
- `GET /api/projects/{projectId}/suite-plans/{planId}`
- `PATCH /api/projects/{projectId}/suite-plans/{planId}/modules/{moduleId}`
- `PATCH /api/projects/{projectId}/suite-plans/{planId}/order`
- `POST /api/projects/{projectId}/suite-plans/{planId}/confirm`

确认响应包含 `batchId`，之后继续使用项目范围的批次读取、取消和槽位重试接口。前端只在 Zustand 保存用于导航便利的 `planId`/`batchId`，页面初始化始终以 `/latest` 和批次读取结果为事实来源。旧本地规划只作为未提交草稿，不自动冒充服务端已确认规划；`mockGenerateSuite` 从真实工作台路径移除。

## Risks / Trade-offs

- [多图输入增大请求体、延迟和 Provider 成本] → 在编译和执行前限制 1–4 张、复用对象存储、记录尺寸与哈希，并由模型能力校验拒绝不支持的组合。
- [严格模块顺序降低整个套图吞吐] → 仅模块之间串行，同一模块槽位并行；不同批次仍可并行执行。
- [模型结构化输出部分缺失或模块键错位] → 服务端进行完整键集合和字段校验，任何模块不合格则规划进入失败状态，不产生半确认规划。
- [确认事务同时写规划和批次，仓储边界变复杂] → 在 PostgreSQL 仓储提供单事务确认方法；内存仓储保持等价语义并用契约测试覆盖幂等与回滚。
- [前序槽位重试时后续模块已经开始] → 阻止尚未领取的后续槽位，允许已经调用 Provider 的槽位完成，避免无法安全撤销的外部调用。
- [正式 RAG 数据源尚未接入] → 以版本解析端口隔离来源；空引用可用，非空引用必须成功解析，绝不静默降级或信任客户端自报内容。

## Migration Plan

1. 新增规划表以及批次来源、规划关联和模块位置字段；为已有批次回填 `kind='hero'`，并按稳定模块任务创建顺序回填连续位置。
2. 先部署兼容旧主图行为的仓储与 Worker；迁移完成并通过就绪检查后再开放详情页规划路由。
3. 部署前端真实规划流程，保留历史项目资产展示，但停止在详情图真实路径写入新的本地模拟结果。
4. 使用假编译器与假图片 Provider 验证规划、确认、有序领取、刷新恢复、取消和重试；真实 Provider 仅在最终人工验收明确确认后调用。
5. 回滚前端时旧页面不会理解服务端规划，但数据保持；回滚后端前需先停止 Worker，再回退应用版本。数据库新增表和兼容字段可暂时保留，避免破坏已生成资产和审计快照。
