## Context

阶段 4 已经持久化详情页规划、模块和套图批次；前端 `BoardPage`/`WorkbenchBoardPage` 已有 React Flow 画布、任务版本选择和布局保存的交互，但相关客户端契约尚未由 FastAPI 提供完整实现。当前设计必须继续遵守单用户、服务端工作区上下文、已发布配置快照和批次 Worker 边界。

## Goals / Non-Goals

**Goals:**

- 建立工作台任务、任务版本、画布布局和资源引用的持久化模型。
- 让工作台刷新恢复、任务编辑、当前/终版选择和布局保存都经过 FastAPI 应用服务。
- 复用阶段 3B/4 的批次确认、Worker、项目资产和规划快照，避免在工作台再次实现生成执行。
- 对任务修订和画布布局版本提供明确的冲突响应。
- 保持已有工作台前端路径和中文错误体验，逐步替换旧接口依赖。

**Non-Goals:**

- 不实现多人实时协作、评论、权限锁、实时推送或冲突自动合并。
- 不实现阶段 6 的图片编辑操作、OCR 或编辑 Provider。
- 不改变阶段 3A/3B/4 的真实 Provider 和 Worker 语义。
- 不做历史 Node 数据的无条件全量回填；没有可验证来源的任务不自动伪造快照。

## Decisions

### 1. 保留现有工作台 HTTP 契约

继续使用客户端已经存在的 `/api/suites/{suiteId}/workbench`、`/tasks`、`/suite-tasks/{taskId}`、版本选择和 `workbench/layout` 路径。这样可以复用已有 BoardPage 交互和类型，减少前后端同时迁移的范围。新服务内部按项目和工作区过滤，不把 suite 路径当作绕过项目边界的特殊入口。

替代方案是新建完整的 `/api/projects/{projectId}/workbench` 版本并长期维护兼容层；该方案命名更统一，但会同时维护两套任务和布局契约，当前阶段不采用。

### 2. 使用四类持久化记录保存工作台事实

- `workbench_tasks`：任务标题、用途、规划项、源图、提示词草稿、生成参数、状态、修订和归档时间。
- `workbench_task_versions`：每次成功生成的不可变图片/提示词/配置/来源快照，并保存 `is_current`、`is_final` 指针语义。
- `workbench_layouts`：每个项目一份当前布局，保存布局版本、视口、节点和分组 JSON；节点只保存业务标识与几何状态，不复制任务事实。
- `workbench_references`：规划或任务到项目资产、输入图、白底图、任务版本或资源库资源的绑定，保存资源版本和来源快照。

所有记录带工作区和项目边界，任务版本与批次/槽位/生成资产通过稳定标识关联。删除资源只会使引用进入归档或不可用状态，不删除历史任务版本。

### 3. 采用应用服务聚合读取和写入

`WorkbenchQueryService` 负责返回工作台聚合视图；`WorkbenchTaskService` 负责任务创建、编辑和生成触发；`TaskVersionService` 负责当前/终版选择；`CanvasLayoutService` 负责布局读写；`WorkbenchReferenceService` 负责引用生命周期。路由只解析请求、注入服务端上下文和映射统一响应，SQLAlchemy、对象存储和批次仓储留在适配器。

工作台进入流程先读取最新已确认规划；若规划项尚无任务，使用持久化幂等键按规划快照创建任务。查询返回任务、批次和布局的一致快照，前端不再用本地模拟对象替代服务端事实。

### 4. 统一使用双层乐观并发控制

任务编辑提交 `expectedRevision`，成功后递增任务修订；布局提交 `layoutVersion`，成功后递增布局版本。版本落后时返回稳定的 409 冲突错误和最新资源，前端提示用户刷新或重新应用草稿。幂等键仍由运行时基线的持久化幂等边界处理，避免重试产生重复任务、引用或选择记录。

### 5. 生成触发只创建/确认批次

工作台单卡或批量生成调用既有批次应用服务，输入是任务当前修订、任务版本快照和已发布配置版本；工作台路由不直接调用 Provider。批次产生的新结果由 Worker 写入任务版本，工作台通过聚合查询或轮询恢复状态。

### 6. 前端保留 React Flow，仅替换数据源

保留当前画布节点投影、拖拽、适应视图和右侧检查器交互。客户端启动时读取工作台聚合和布局，节点位置/视口变更通过防抖队列保存；遇到布局冲突先读取最新布局，再由用户重新操作。任务提示词和参数保存成功后刷新选中任务，避免旧闭包状态继续提交。

## Risks / Trade-offs

- [风险] 旧 Node 任务结构与新任务表字段不完全一致 → 仅对有明确规划快照和版本来源的记录做适配；无法验证的旧记录保留在旧路径，不自动伪造新快照。
- [风险] 任务版本 JSON 快照增大数据库记录 → 只保存生成所需的不可变摘要、哈希和对象引用；原图继续由对象存储管理。
- [风险] 画布频繁拖动产生大量写请求 → 前端防抖并串行保存，服务端以布局版本拒绝过期写入。
- [风险] 工作台查询聚合多个资源导致响应变慢 → 先限制为单项目单工作区，按任务和版本批量读取，并为项目/任务/引用字段建立索引。
- [风险] 任务状态与批次状态短暂不一致 → 批次仍是生成执行事实来源，工作台显示带更新时间的聚合状态，刷新或轮询后最终一致。

## Migration Plan

1. 增加工作台四类表和必要索引，不修改既有规划、批次和项目资产表的历史数据。
2. 增加内存和 PostgreSQL 仓储、应用服务及 FastAPI 路由；为已确认规划提供幂等任务创建入口。
3. 将现有客户端方法接到 FastAPI，并补齐任务编辑、版本选择、布局冲突和引用生命周期测试。
4. 在受控环境中执行 Alembic 前向迁移；回滚只移除新增工作台表，不触碰已有生成结果和项目资产。
5. 通过刷新恢复、并发修订和资源范围测试后，再进行统一人工验收；本变更不调用真实计费 Provider。
