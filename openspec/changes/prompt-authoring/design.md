## Context

提示词商城（`prompt_library`）已具备模板、版本、分类和 `stage` / `execution_target` 维度，但只有读取与测试能力。生成侧的提示词编译（`OpenAICompatiblePromptCompiler`、`OpenAICompatibleSuitePlannerCompiler`）产出的是**单模块、一次性**的实时任务提示词，不形成可复用资产。因此「模板从哪来」始终缺一环。

项目另有一份未实现的爆品图反推原型：`src/pages/ReversePage.tsx` 挂在 `src/app/App.tsx` 上，而 `src/main.tsx` 实际挂载的是 TanStack Router（`src/routes/router.tsx`），`App.tsx` 从未被引用；后端也没有对应接口。原型的数据结构（Plan / Ref / Attempt / PromptVersion / baselineReferenceId）与交互（4 步流程、主图与详情图两种反推类型、16 张上限、逐图选模板、批量反推、系列色彩基准、带入共享画布）仍有参考价值。

本设计必须继续遵守项目既有约束：单用户、服务端工作区上下文、生成只读已发布配置、不可变快照、Alembic 唯一迁移入口、内存与 PostgreSQL 双仓储。

## Goals / Non-Goals

**Goals:**

- 提供描述创作、爆品图反推、改写生成三种输入方式，统一产出可复用提示词模板。
- 生成结果直接对齐商城模板字段，确认后可立即在商城测试、绑定和版本化。
- 让平台合规要求在模板生成阶段就进入提示词，而不是在图片生成阶段事后补救。
- 复用既有 `prompt_templates` / `prompt_versions`，不引入新的业务表。
- 反推能力支持逐图独立控制与批量执行，并支持详情图系列的色彩基准约束。

**Non-Goals:**

- 不持久化反推会话、参考图与逐图尝试；刷新后中间态丢失，需要重新上传。
- 不保存爆品参考图为项目资产。项目素材语义是「自己的商品」，爆品参考图不属于该语义；后续如需归档再单独设计 `reverse_reference_asset` 边界。
- 不调用图片生成 Provider。本变更只生产提示词，不产生图片计费。
- 不实现原型的「带入共享画布」。该能力依赖工作台引用边界，本变更不涉及。
- 不删除早期原型死代码。反推重建完成前保留 `ReversePage.tsx` 作为设计参考。
- 不实现多用户协作、审核流或模板市场分发。

## Decisions

### 1. 复用 prompt_library，不新增业务表

生成产出的模板写入既有 `prompt_templates` + `prompt_versions`；`prompt_versions.source` 字段（现有默认值 `marketplace`）用于标记 `generated` / `manual` / `imported`，反推来源、输入摘要和生成时间写入 `applicability` 或 `change_note`。

替代方案是新建 `prompt_authoring_sessions` + `prompt_authoring_drafts` 记录生成过程。该方案能保留中间态，但会让「生成出来的模板」和「手写的模板」长期分属两套模型，商城必须同时查询两处才能展示完整内容。当前阶段不采用。

### 2. 产出必须是结构化草稿，不是自由文本

模型返回的必须是可直接落库的结构化对象，而不是一段文字后再由人拆解：

- `body`：提示词主体
- `user_prompt_template`：带变量的用户提示词模板
- `input_schema`：变量声明（名称、类型、是否必填、示例）
- `output_schema`：期望输出结构
- `applicability`：适用平台、品类、模块、反推来源等
- `generation_params`：建议的模型与参数

替代方案是先产出自由文本、再由解析器抽取。该方案对模型格式遵循度要求更高且失败模式不透明，用户看不到「模型到底理解成了什么」。采用结构化输出后，草稿在界面上按字段分块展示并可直接编辑，落库时无需二次解析。

### 3. 标准变量集作为强制契约

定义一套标准变量名（平台、市场、语言、品类、卖点、风格、模块），所有生成结果的 `user_prompt_template` 必须只使用这些变量。生成后做一次校验，出现未登记变量则退回重生成或要求用户修正。

替代方案是允许模板自定义任意变量。该方案短期更灵活，但会让模板无法在生成配置中心被绑定复用——绑定方无从知道要传什么。标准变量集是模板可被复用的前提。

### 4. 平台合规规则在生成阶段注入

新增平台规则读取模块，从 `config/platform-image-rules.json` 按平台读取主图尺寸、格式、体积、背景要求、产品占比、是否允许文字/水印/边框等约束，并转换为提示词片段注入生成过程。

该模块同时供既有生成约束卡使用（`hero_prompting.resolve_constraint_cards` 当前只使用 `market.guidance` 字符串，未读取平台规则文件）。两处共用一个读取模块，避免规则出现两份解释。

### 5. 反推由商城模板驱动

反推本身使用 `stage=reverse_prompt` 的提示词模板作为元提示词，而不是把反推指令硬编码在代码里。这样反推质量可版本化、可对比、可迭代；反推出的新提示词又进入同一个商城，形成正循环。

替代方案是把反推指令写死在服务端。该方案改一次要发一次版，且无法针对不同品类调优。不采用。

### 6. 反推中间态不持久化

反推会话（方案、参考图、逐图尝试、色彩基准选择）保存在前端会话态。参考图以 multipart 直接提交给生成接口，服务端处理完即丢弃，不写入对象存储。

代价是刷新后中间态丢失，用户需要重新上传。收益是本变更不引入新表、不引入参考图生命周期与孤儿清理问题，范围可控。若后续确认该体验不可接受，再以独立变更引入会话持久化。

### 7. 前端重建而非复活废弃路由

反推页面按原型的设计意图重建为 TanStack Router 路由，复用现有设计系统与 `src/api/client.ts`。不复活 `src/app/App.tsx`——项目同时存在两套路由本身就是隐患，本次排查中已出现过被废弃原型误导的情况。

原型值得继承的三点：主图/详情图二分、每张参考图独立选模板与独立重跑、详情图以第 1 张或指定图建立系列色彩基准。

## Risks / Trade-offs

- **模型输出不稳定** → 结构化草稿可能缺字段或变量不合法。缓解：生成后做字段完整性与变量集校验，失败时明确提示并允许用户手工补齐，不静默落库。
- **不持久化中间态影响体验** → 上传 16 张图后刷新会全部丢失。缓解：界面上明确提示；批量反推结果可逐条复制；确认保存的模板已进商城不受影响。
- **平台规则与真实平台要求可能过期** → `platform-image-rules.json` 是静态文件。缓解：规则注入的内容在草稿界面可见，用户可核对；规则文件更新不需要改代码。
- **生成模板质量参差** → 生成不等于可用。缓解：草稿必须经用户确认才落库；商城已有的测试与对比标签页可直接用于验证。
- **元提示词自身质量决定反推上限** → 若反推模板写得差，反推结果也差。缓解：元提示词可版本化，可在商城里迭代对比。
