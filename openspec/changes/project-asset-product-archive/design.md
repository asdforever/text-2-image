## Context

项目资产域已持久化项目源图、白底图和生成图片，并负责对象存储、预览、选择与清理。正式成品库拥有产品和版本表，但只在生成完成或手工发布时创建记录，且 PostgreSQL adapter 尚未覆盖全部路由方法。旧规格把正式成品限定为显式发布版本；本变更按 proposal.md 和能力规格调整为“项目创建即建档，项目全资产自动汇总”。

## Goals / Non-Goals

**Goals:**

- 每个工作区维持一个自动项目成品库，每个项目维持一个产品条目。
- 将项目资产作为图片事实来源，成品档案通过关系表聚合，不复制对象存储内容。
- 生成图片在项目资产关联之外继续保存不可变版本快照。
- 项目创建、资产新增、资产删除和项目归档通过统一协调边界保持一致。
- 为现有项目和资产提供幂等回填。

**Non-Goals:**

- 不把提示词测试结果直接写入正式成品库。
- 不把成品库变成另一套对象存储或项目资产副本。
- 不在本变更中实现多人权限、审批流、标签体系或跨项目资产共享。
- 不自动删除仍被版本、任务或其他资产引用的对象文件。

## Decisions

### 1. 项目资产是媒体事实来源

新增 `product_asset_links` 关系表，保存产品条目与项目资产的一对一关联。关系表记录工作区、项目、产品、资产和创建时间，不复制文件名、尺寸、哈希或对象键；查询时从 `project_assets` 与 `asset_objects` 读取最新媒体信息。

相比把源图伪装成 `product_versions`，关系表允许手动上传资产没有生成状态和提示词快照，也避免扩大 `product_versions.product_type` 的正式版本语义。

### 2. 统一协调器保证项目生命周期一致

新增项目成品档案协调接口：

- `ensure_project_archive(project)`：创建或复用“项目成品库”和项目产品条目。
- `link_project_asset(project, asset)`：确保档案存在并幂等创建资产关联。
- `unlink_project_asset(project_id, asset_id)`：删除资产关联。
- `archive_project_archive(project_id)`：归档对应产品条目。
- `backfill_workspace()`：扫描当前工作区的项目和资产并补齐关系。

项目服务和项目资产服务通过可选依赖调用该接口。内存测试可注入内存实现；数据库运行时使用 PostgreSQL 实现。协调器内部处理唯一冲突和重读，调用方无需了解成品库表结构。

### 3. 数据库约束承担幂等底线

为活动项目产品建立 `(workspace_id, project_id)` 条件唯一索引；为资产关联建立 `(product_id, project_asset_id)` 唯一约束，并约束关联中的工作区和项目。应用幂等与数据库唯一约束共同处理请求重放和并发首次写入。

自动项目成品库通过稳定的 `library_type = 'production'` 与固定系统标识识别。为了兼容现有表结构，系统标识放入库记录的元数据能力无法直接使用，因此第一版以工作区内保留名称“项目成品库”和唯一约束共同定位，并禁止前端归档该系统库。

### 4. 创建和关联采用同步事务边界

项目创建接口在返回 `201` 前确保产品条目已存在；资产上传和 Worker 写入项目资产后，在返回成功或标记任务成功前确保资产关联已写入。若关联失败，请求返回依赖失败，资产记录保留用于重试，避免删除已经成功写入的图片。

为解决跨服务事务无法原子提交的问题，协调器操作全部幂等，且 `backfill_workspace()` 可补偿孤立项目或资产。日志记录项目和资产标识，便于重新执行补齐。

### 5. 生成版本继续关联项目资产

`product_versions.source_version_id` 继续记录项目资产或任务版本来源，`source_snapshot` 明确保存 `assetId`。成品库详情先展示全部项目资产，再把同一 `assetId` 的生成版本快照附加到资产；同一来源版本只创建一次。

### 6. 前端从手工发布改为项目聚合浏览

正式成品库列表只展示自动项目成品库和项目数量；详情页按项目显示条目。项目产品详情展示资产缩略图、资产类型、来源、生成版本状态和打开项目按钮。移除手工产品创建、成功版本标识和来源快照 JSON 输入。

### 7. 提示词测试成功后自动进入统一测试库

提示词测试执行器在图片生成并完成对象存储上传后，于同一数据库事务中创建测试成品并回写测试任务的 `output_product_id`。系统复用统一的“测试结果”库，不为每个提示词创建独立库；测试成品保存测试任务、提示词版本、输入素材或文本、生成参数、模型和耗时等来源快照。

`test_run_id` 作为测试成品的幂等标识并建立唯一约束。执行器重试或完成回调重放时复用已有测试成品，不重复写入；失败任务只记录失败状态和错误信息，不创建测试成品。提示词商城在任务完成后直接显示“已自动保存到测试库”和打开测试库入口，移除下载结果再上传的旧“保存到成品库”流程。

## Risks / Trade-offs

- [项目创建成功但档案写入失败] → 接口返回依赖失败，项目保留；后续重放或回填幂等补齐。
- [资产已保存但关联失败] → 保留项目资产并记录失败，页面仍可从项目读取；回填恢复成品档案关系。
- [历史项目数量较多导致回填耗时] → 按工作区和主键分页执行，每批独立提交并输出计数。
- [项目名称修改后产品名称过期] → 查询和回填时同步产品显示名，项目标识保持唯一。
- [已有重复项目产品] → 迁移前只读检测并选择最早活动条目为主条目，迁移关系后归档重复条目，再建立唯一索引。

## Migration Plan

1. 新增 `product_asset_links` 表、索引和项目产品条件唯一索引；迁移不复制或删除图片对象。
2. 部署完整 PostgreSQL 成品库 adapter 与项目成品档案协调器。
3. 接入项目创建、资产新增、资产删除、项目归档和生成 Worker。
4. 执行一次幂等回填，为已有项目和资产建立档案关系，并记录创建、复用和失败计数。
5. 部署按项目聚合的成品库前端，移除手工产品和版本输入。
6. 为测试成品增加 `test_run_id` 唯一约束，并部署提示词商城自动入库状态与测试库入口。
7. 回滚应用时保留新增表和关系数据；旧版本应用会忽略它们，不影响项目资产读取。
