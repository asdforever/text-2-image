## Context

现有 `suite_workbench` 仅为 `/api/suites` 和输入图片提供最小聚合，`prompt_library` 的 `assets/products/test_runs` 服务于提示词商城测试。二者都不表达工作台项目中的素材角色、版本链路、当前选择与对象引用状态。

阶段 0 已提供服务端身份上下文、统一错误信封、持久化幂等和“路由 -> 服务 -> 端口 -> 适配器”分层。本设计在这些边界内新增项目资产域；动机与对外行为见 `proposal.md` 和两个能力规格。

## Goals / Non-Goals

**Goals:**

- 为项目、资产对象、项目资产引用和当前选择建立可查询、可迁移的关系模型。
- 在同一写入流程内协调对象存储、数据库元数据、幂等记录和失败补偿。
- 以清晰的 API 与服务边界支持后续配置快照、真实生图结果、套图和图片编辑。
- 不破坏现有 `/api/suites`、`/api/asset-libraries` 及其测试契约。

**Non-Goals:**

- 不将现有 suite 数据迁移为项目，不修改前端以外的既有 suite 语义。
- 不调用抠图、白底图或真实图片生成 Provider，也不实现队列/Worker。
- 不实现用户认证、多工作区管理、跨工作区共享、CDN 策略或最终的后台垃圾回收调度器。
- 不将项目资产与提示词商城资产、产品或测试运行表合并。

## Decisions

### 1. 新建独立的 `project_workbench` schema

增加以下关系：

| 关系 | 责任 | 关键字段 |
| --- | --- | --- |
| `projects` | 项目生命周期与工作区范围 | `id`、`workspace_id`、`name`、`status`、`archived_at`、时间戳 |
| `asset_objects` | 物理对象及清理状态 | `id`、`workspace_id`、`storage_key`、媒体元数据、`sha256`、`state`、`cleanup_attempted_at` |
| `project_assets` | 项目内可见资产与角色、版本链路 | `id`、`project_id`、`object_id`、`kind`、`source_asset_id`、`generation_snapshot_id`、`state` |
| `project_asset_selections` | 每个项目角色的当前选择 | `project_id`、`role`、`project_asset_id` |

项目和物理对象分离，项目资产是项目对对象的领域引用。`source_asset_id` 用于白底图版本溯源，`generation_snapshot_id` 在阶段 3A 前允许为空。外键、检查约束和唯一索引保护工作区归属、合法 `kind/state` 和同一角色的唯一当前选择。

替代方案是把字段追加到 `suite_workbench.input_images`，或直接复用 `prompt_library.assets`。前者会把项目生命周期强绑到已兼容的旧接口，后者会混淆工作台与提示词测试的所有权和删除语义，因此不采用。

### 2. 项目 API 使用新资源路径，旧 suite 保持兼容

新增 `/api/projects`、`/api/projects/{projectId}` 及其 `/assets` 子资源，提供创建、列表、详情、归档、删除、上传、选择、取消选择、删除和预览。所有 JSON 成功与错误继续使用既有响应信封和请求 ID 规则；上传、选择、归档、删除等副作用操作使用阶段 0 的幂等服务。

项目详情包含资产摘要、按类别的资产列表和当前选择；列表默认排除归档项目，并由显式筛选加入归档项。预览通过受控后端响应或短时预签名 URL 实现，且服务层先按当前工作区校验项目与资产关系。

替代方案是立即把 `/api/suites` 别名为 `/api/projects`。这会令前端兼容和旧切流边界发生变化，收益不足，推迟到后续明确迁移变更。

### 3. 文件存储使用项目专属 key 与两阶段补偿

新增面向项目资产的对象存储端口，而不是让路由调用 `AssetMinioStorage` 或 `ObjectStorage` 具体实现。对象 key 按 `projects/{workspace_id}/{project_id}/{asset_id}/...` 生成，应用服务在校验通过后先写入对象，再在数据库事务中写入对象记录、项目资产和幂等完成记录。

数据库失败时服务删除刚写入的对象；删除对象失败则创建/保留 `cleanup_pending` 状态供同一服务的显式重试入口处理。服务绝不按目录批量删除，也不根据客户端提供的 key 删除。数据提交后返回的仅是项目范围内的资产视图，未完成或待清理记录不作为可选素材暴露。

替代方案是“数据库先写、对象后写”。该方式在对象写入失败时会暴露无法预览的资产，补偿更复杂，故不采用。

### 4. 删除以引用判断为准，不做隐式物理删除

删除项目资产时，服务首先锁定资产引用，判断是否仍被其他项目资产、白底图来源链路或生成快照引用。仍被引用时，拒绝硬删除或仅移除允许解除的项目可见关系；无引用时标记对象为 `cleanup_pending`，在对象删除成功后把资产记录转为已清理状态。删除项目复用这一逻辑逐项解除引用。

阶段 1 提供可测试的同步清理尝试和明确的待清理状态，不引入独立 worker。阶段 3A/3B 新增生成快照和任务时，只需把它们加入同一引用判断。

### 5. 用服务与仓储端口隔离领域逻辑

新增 `ProjectService`、`ProjectAssetService` 和对应 repository/storage 协议；HTTP 路由只解析请求并映射响应。PostgreSQL/MinIO 适配器作为默认生产实现，内存仓储/存储作为单元和 HTTP 契约测试实现。更新现有路由架构静态护栏，禁止新项目路由直接访问数据库会话、MinIO 客户端或具体存储方法。

该选择延续阶段 0 的依赖替换能力。直接在路由中复用现有 SQLAlchemy 服务虽快，但会重新引入已建立的层次违规，不采用。

## Risks / Trade-offs

- [风险] 资产对象与项目资产两层记录增加查询复杂度 → 缓解：详情查询在仓储内预加载必要关系，路由只消费稳定视图。
- [风险] 对象存储和数据库无法形成分布式事务 → 缓解：限定写入顺序、记录可重试清理状态，并为每个失败路径编写契约测试。
- [风险] 同一对象的跨项目共享需求在阶段 1 尚未有 UI → 缓解：数据模型支持引用计数式判断，初始 API 只在同工作区内创建项目资产，暂不开放跨项目复制入口。
- [风险] 历史 suite 与新项目双轨并存造成概念混淆 → 缓解：API 文档明确其兼容定位，前端新功能只接入 `/api/projects`。
- [风险] 迁移影响既有远程数据库 → 缓解：仅新增 schema 和表，使用 Alembic 单一迁移入口；不修改或删除旧 schema。

## Migration Plan

1. 在 Alembic 新 revision 中创建 `project_workbench` schema、项目/对象/资产/选择表、外键、检查与索引；同时更新 migration checksum 预期值。
2. 部署时先运行既有迁移预检查和显式 `alembic upgrade head`，不在应用启动时执行 DDL。
3. 发布后新 `/api/projects` 为空，但既有 suite、提示词素材与对象保持不变；前端可逐步改用新 API。
4. 回滚优先撤回路由流量和前端调用，不删除新表、项目记录或对象。只有在确认新域没有数据且已备份时，才执行经过专用测试库验证的 Alembic downgrade。

## 前端接入边界

项目管理页直接消费 `/api/projects`，只展示服务端持久化的名称、状态和更新时间；原本仅存在于浏览器内的商品名称、默认分类和产物数不写入项目域。创建、归档和删除完成后重新读取项目列表。

项目工作台打开时读取 `/api/projects/{id}`，并把源图与白底图资产映射为现有的卡片、素材面板和版本面板视图。图片预览始终使用受控的 `/preview` 地址，前端不保存对象存储 key。基础图页支持上传原图、为选定原图上传白底图、设为当前使用、删除和导出；所有写操作完成后重新读取项目详情。

主图、详情套图、视频、生成配置与真实图片生成不属于本次接入。它们继续使用现有前端状态，不能把本次的项目 API 误当作生成任务 API；基础图页面明确显示当前阶段只管理上传版本，不触发生成模型。
