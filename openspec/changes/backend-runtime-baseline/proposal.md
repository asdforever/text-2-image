## 为什么

当前 FastAPI 后端已经具备基础健康检查、项目素材上传、提示词和素材库能力，但运行时边界仍不统一：部分路由直接访问数据库，迁移入口有两套，前端工作台所需的接口尚未有稳定的服务层契约。继续在这个基础上叠加生成业务，会让单用户草稿、未来工作区隔离、幂等和错误处理分散在各个路由中，增加后续接入真实生图和多用户认证的迁移成本。

现在先建立一个可替换的单用户运行时基线，可以让后续业务模块按同一方式实现和逐步验收，同时保留未来身份认证和多工作区的扩展边界。

## 变更内容

- 新增身份上下文接口，当前由本地单用户适配器提供固定 `actor_id` 和 `workspace_id`；客户端不得自行指定工作区。
- 统一 API 路由、应用服务、领域规则、仓储/适配器的依赖方向，禁止业务路由直接拼接 SQL 或调用对象存储客户端。
- 统一 PostgreSQL 迁移入口、版本检查和升级/回滚验证，明确迁移文件的唯一来源。
- 统一成功响应、错误信封、请求 ID、稳定错误码和需要副作用的请求的幂等策略。
- 为现有 suite/input-image 垂直切片补充 OpenAPI 契约测试、依赖故障测试和 Node/FastAPI 并行运行验证。
- 保持现有 `/api/suites` 和素材上传接口兼容；本阶段不实现真实生图、任务队列、登录、权限或多租户业务。

## 能力范围

### 新增能力

- `backend-runtime`: 提供单用户身份上下文、运行时依赖注入、服务分层、统一响应错误契约和幂等边界。
- `backend-migration-boundary`: 提供数据库迁移的唯一入口、版本校验、升级/回滚和并行部署约束。

## 影响范围

- 影响 `backend/app/main.py`、核心上下文、路由、Repository、数据库迁移入口和后端测试目录。
- 需要整理现有资产、产品和测试运行路由，使其遵循统一响应和服务依赖方向，但不改变本阶段已经对外使用的路径。
- 需要在配置中保留本地工作区标识，并为未来认证适配器预留接口；不会新增登录依赖。
- 需要验证 FastAPI 与现有 Node 服务可在不同端口并行运行，前端代理只切换已声明的路径。
