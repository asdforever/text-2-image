## 上下文

动机和范围见 `proposal.md`。当前 FastAPI 应用已经具备应用工厂、请求 ID 中间件、异步 SQLAlchemy、对象存储适配器以及 suite/input-image 路由，同时 Alembic 迁移图和旧版 SQL 迁移运行器并存。资产、产品和测试运行路由仍直接访问 SQLAlchemy 会话，而前端工作台期望所有接口使用一致的响应信封。

第一版是单用户、单工作区，但未来增加认证和多工作区隔离时，不应重写应用服务和仓储。

## 目标与非目标

**目标：**

- 建立无需认证服务也能运行的服务端身份/工作区上下文。
- 让 HTTP 处理器依赖应用服务和稳定端口，而不是数据库或存储客户端。
- 让 Alembic 成为唯一 schema 迁移权威，并提供确定性的漂移、并发、升级和回滚检查。
- 在重组实现时保持现有 suite/input-image API 路径和响应兼容。
- 通过测试和本地部署文档证明 FastAPI/Node 可选择性切流并安全回滚。

**非目标：**

- 不实现登录、令牌签发、授权界面或租户管理。
- 不实现图片/LLM Provider 适配器、持久化生成队列或后台 Worker。
- 不把公开的 `suite` API 重命名为 `project`；术语统一留待兼容方案确定后处理。
- 不在一次变更中迁移所有业务路由；本阶段只迁移已声明的垂直切片并定义边界。

## 技术决策

### 1. 服务端拥有身份上下文，本地适配器提供默认值

定义包含 `actor_id`、`workspace_id` 和角色声明的应用上下文端口。默认适配器从配置读取稳定 UUID，在本地每个请求返回相同值。路由不接受客户端提交的身份值作为权威来源，仓储方法显式接收上下文并对所有读写应用工作区过滤。

这样能保持单用户部署简单，同时允许未来只替换身份适配器即可接入会话/JWT。客户端提交的工作区 ID 必须被忽略或拒绝，不能作为数据范围选择器。

### 2. 保留外部 suite 路由，内部允许领域别名

保留 `/api/suites` 和 `suite_id`，因为当前前端和 Node 服务都依赖它们。应用服务内部可以将聚合称为项目/工作区资源，但本阶段不改变公开契约。未来改名时应增加明确别名和迁移测试，不得静默改变标识。

### 3. 采用“路由 -> 服务 -> 端口 -> 适配器”分层

增加依赖组合层，统一构造应用服务所需的仓储、存储、时钟、身份和幂等端口。路由只负责请求解析、身份上下文获取和响应映射；领域校验及跨资源不变量放在服务/领域规则中；SQLAlchemy 和 MinIO 实现留在适配器内。

迁移采用增量方式：先包装现有仓储实现，再把资产、产品和测试运行路由中的直接 SQL 移入服务方法，避免一次性重写，同时建立唯一依赖方向。

### 4. 集中处理响应、错误和请求 ID

复用现有请求 ID 上下文，但将信封和错误构造集中到一个 API 工具。校验失败、资源不存在、依赖故障、唯一键冲突和幂等冲突都映射为稳定应用错误码。错误序列化时用请求 ID 记录内部异常，但对外不暴露 SQL、堆栈、密钥、桶名称或任意对象 key。

### 5. 在应用边界使用持久化幂等记录

所有本阶段有副作用的接口都使用由 PostgreSQL 支持的幂等端口。记录保存作用域（方法、规范化路由/资源）、请求指纹、状态和序列化响应。服务尽量在与领域写入同一事务中声明幂等键；等价重试返回已保存响应，指纹不一致则返回冲突。内存缓存只能优化性能，不能作为事实来源。

### 6. Alembic 作为唯一迁移权威

提交到仓库的 Alembic 迁移图成为新 schema 变更的唯一来源，也是 CI 和部署的唯一入口。旧版 `backend/app/migrations.py` 仅保留兼容用途，不用于新表或启动时变更；相关测试改为检查不得存在并行迁移来源。

对于已有数据库，部署先验证 schema 形状，再记录或 stamp 对应的 Alembic 基线。旧 `schema_migrations` 记录保留作审计，但不再独立执行。每个 revision 必须保持唯一 head、确定的 revision 标识，并在数据库支持时提供经过测试的 downgrade。

### 7. 显式迁移和选择性切流

应用启动只检查迁移状态，不自动执行待处理 DDL。单独的 CLI/CI 命令在数据库 advisory lock 下执行升级。上线期间代理只把本变更声明的 suite/input-image 路径转给 FastAPI，其余路径继续转给 Node。停止 FastAPI 只影响流量，不触发数据库或 MinIO 清理。

### 8. 先验证边界，再增加业务域

使用 HTTPX 契约测试，并覆盖身份、仓储、存储和幂等依赖替换。增加可选 PostgreSQL 迁移锁/漂移测试，以及同时启动两套服务、切换路径、再切回并读取同一数据的部署冒烟测试。这些测试会成为后续生成模块复用的验收基础。

## 风险与取舍

- [风险] 增加工作区列或范围过滤时暴露旧数据不一致 -> 缓解：在专用迁移中把现有记录回填到本地工作区；仍有未归属记录时就绪检查失败。
- [风险] 停用旧迁移运行器后，旧数据库无法识别 -> 缓解：提供一次性的 schema 校验/stamp 流程，并将旧记录保留为只读审计数据。
- [风险] 增量抽取服务导致路由模式混杂 -> 缓解：为已迁移路由增加禁止直接访问会话和存储客户端的静态检查，并明确记录尚未迁移的路由。
- [风险] 单工作区没有用户级隔离 -> 缓解：将部署标记为本地专用，并强制使用身份端口，禁止依赖客户端范围值。
- [风险] 选择性代理导致 Node 与 FastAPI 行为差异 -> 缓解：切流前对两个目标执行同一组 API 契约用例。

## 迁移计划

1. 增加本地身份/工作区上下文的配置和依赖组合；如 schema 需要，为现有 suite 范围记录回填稳定本地工作区。
2. 集中响应、错误和请求 ID 工具，在不改变公开路径的前提下让 suite/input-image 垂直切片通过应用服务执行。
3. 让 Alembic 成为唯一活动迁移入口，增加基线验证、漂移检测、锁测试和显式升级/回滚命令；旧运行器标记为仅兼容用途。
4. 为 suite 创建和 input-image 上传增加持久化幂等处理，覆盖重放和幂等键冲突测试。
5. 并行运行 FastAPI 和 Node，执行选择性代理、回滚冒烟和就绪检查。

回滚优先采用流量回滚：将所有路径切回 Node 并停止 FastAPI，不删除 schema、迁移元数据、数据库记录或对象。若必须回退 schema revision，应先按部署策略备份数据库，再执行经过测试的 Alembic downgrade。
