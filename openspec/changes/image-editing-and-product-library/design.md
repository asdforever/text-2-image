## Context

现有项目资产域已经负责项目内源图、白底图和生成图片的对象存储、预览、选择与清理；工作台前端已有图片编辑器和 OCR API 边界，但后端尚未持久化编辑会话。提示词商城另有素材库和测试产物库，正式产品成品不能复用其业务记录。详见 proposal.md 及两份能力规格。

## Goals / Non-Goals

**Goals:**

- 建立图片编辑会话、操作、OCR、任务、尝试和版本的服务端状态机。
- 将成功的项目图片版本以不可变来源快照发布到正式产品库。
- 复用现有对象存储和项目范围校验，保证幂等、乐观修订和可追溯。
- 保持单用户部署，同时保留 workspace_id、actor_id 接口边界。

**Non-Goals:**

- 本阶段不实现多人实时协作、评论、权限锁或实时画布同步。
- 不把编辑草稿、蒙版和操作日志直接当作正式产品成品。
- 不接入真实计费 Provider；生成执行继续通过既有批次/Provider 端口。
- 不改变提示词测试产物库的历史数据语义。

## Decisions

### 1. 编辑域与产品域分离

新增独立的编辑会话和正式产品资产表，通过 `source_version_id`、`task_id`、`attempt_id` 建立只读来源关系。相比把字段直接塞入现有 `project_assets`，分离可以保持项目素材上传契约稳定，并允许一个编辑会话产生多个任务和版本。

### 2. 不可变快照加指针

任务提交和产品发布时保存 JSON 快照（操作、提示词、配置、源图信息），同时使用 current_version_id/final_version_id 指针表达当前选择。后续编辑不会改写历史快照；指针更新使用乐观修订。

### 3. 异步执行复用既有生成边界

`POST /image-editor/sessions/{id}/submit` 只负责校验、落库和入队，返回 queued 任务。批次 worker 负责调用 image editor Provider、写入尝试和版本；这样工作台 API 不直接暴露 Provider，也能复用现有重试和幂等机制。

### 4. 正式产品库采用发布动作

项目素材上传、素材库导入和测试产物都不自动进入正式产品库。新增显式发布接口，以来源版本和幂等键为唯一约束创建产品版本；发布成功后产品库只读保存来源快照，编辑域仍可继续产生新版本。

### 5. 统一对象引用清理

编辑版本和正式产品版本均引用现有对象存储记录。删除采用“先解除业务引用、再按引用计数清理对象”的策略，失败写入 cleanup_pending，沿用现有重试任务而不做不可逆级联删除。

### 6. API 兼容前端现有边界

实现前端已使用的 capabilities、sessions、operations、submit、tasks、attempts/retry、regenerate、ocr 和 versions/select 路径；响应统一包含 `revision`、状态和来源快照。正式产品库新增 `/api/product-libraries`、`/products`、`/versions/publish` 等 REST 路径，并保留单用户默认身份解析。

## Risks / Trade-offs

- [快照 JSON 体积增长] → 对操作和配置设置大小限制，并在列表接口返回摘要，详情接口返回完整快照。
- [Provider 异步失败导致孤儿对象] → 事务提交后再写对象，失败尝试可重试；对象写入异常走现有补偿清理。
- [旧 ProductLibrary 类型命名不一致] → 阶段六新增正式类型枚举并提供兼容映射，保留测试产物库的 `test` 语义，不迁移历史记录。
- [前端本地状态与服务端状态短暂不一致] → 所有写接口返回最新修订和实体，前端提交成功后以服务端响应覆盖本地草稿。

## Migration Plan

1. 执行新增表和索引迁移，不修改现有项目资产和测试产物记录。
2. 部署只读查询和会话草稿接口，再启用提交/worker 写入。
3. 部署正式产品库发布接口和前端发布入口；历史测试产物继续留在原库。
4. 观察对象清理失败、任务重试和版本指针冲突指标；必要时可通过关闭发布入口回滚，已写入的历史版本保持可读。

## Open Questions

无。Provider 的具体模型和计费策略沿用既有配置，不影响本阶段接口契约。
