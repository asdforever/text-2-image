## Context

阶段 3A 的 `hero_generation_tasks` 将“编译提示词、用户确认、同步生成一张图片”保存在单条记录中，且服务端与前端都强制一个模块、一张结果。`ModuleSelector` 已提供每模块 1-4 张的草稿控件，但该值尚未进入真实任务系统。见 `proposal.md` 了解变更动机，见规格了解对外行为。

## Goals / Non-Goals

**Goals:**

- 建立可由主图、后续套图和编辑任务复用的持久化批次、模块和图片槽位编排基础。
- 让用户在调用图片 Provider 前审阅每个模块的一条任务提示词，并把 1-4 张作为该模块的结果槽位数。
- 通过数据库租约让独立 Worker 安全执行可重试的等待槽位，保留单张结果、失败和尝试历史。
- 保持阶段 3A 的提示词编译、约束卡、Provider 适配器、项目资产服务和历史记录可用。

**Non-Goals:**

- 不把套图、视频、画布持久化或图片编辑迁入本变更。
- 不增加自动重试、自动补图、跨项目共享任务或多用户调度。
- 不承诺中断第三方图片 Provider 的网络调用；只提供受控的取消请求和结果丢弃。
- 不迁移或重写已有 `hero_generation_tasks` 与生成资产。

## Decisions

### 1. 批次、模块任务、槽位和尝试分层保存

新增 `generation_batches`、`generation_module_tasks`、`generation_image_slots` 和 `generation_slot_attempts`。批次承载项目、源图和全局不可变快照；一个模块任务承载一条编译/确认后的实时任务提示词及该模块约束快照；每个槽位代表一张期望结果；尝试记录每次 Worker 领取和 Provider 调用的安全摘要。

阶段 3A 单表不扩展为多结果表：它的确认幂等和同步状态机已与单张资产耦合。复制整张任务记录会让批次状态、取消和尝试历史分散且难以聚合。新表与既有任务并存，历史资产继续引用原任务 ID。

### 2. 每模块确认一条提示词，槽位作为结果变体

批次编译时对每个模块分别调用现有视觉提示词编译端口，产生各自的可见事实、无法确认项和实时任务提示词。确认批次时，用户仅提交模块 ID 到编辑后提示词的映射；服务端确定性组合真实性、平台、风格和模块任务段，并为数量 1-4 创建槽位。

同一模块的槽位共享冻结的最终提示词但使用独立 Provider 请求，形成结果变体。这避免用户为同一模块重复编辑同一指令；若未来需要逐张差异提示词，可在模块任务下增加槽位提示词覆盖字段，不改变批次边界。

### 3. 采用数据库队列与独立 Worker，而非请求内后台任务

确认 API 只在事务中冻结快照、创建槽位并返回批次。独立 `generation-worker` CLI 循环以 `FOR UPDATE SKIP LOCKED` 领取待执行槽位，写入短租约和尝试记录后再调用 Provider。并发数由环境设置控制，默认 1；Worker 启动和关闭不依赖浏览器会话。

FastAPI `BackgroundTasks` 与浏览器轮询都不能在进程重启后恢复。外部队列会增加部署依赖，当前单用户版本不需要；PostgreSQL 已是项目依赖，数据库队列能提供持久领取和可查询状态。

### 4. 区分可恢复领取与结果不确定的 Provider 调用

槽位状态包含 `queued`、`leased`、`dispatching`、`succeeded`、`failed`、`cancel_requested`、`cancelled` 和 `needs_retry`。Worker 在 Provider 调用前把槽位置为 `dispatching` 并记录带唯一上游幂等键的尝试；若租约在尚未开始调用时过期，其他 Worker 可以重新领取。若进程在 `dispatching` 后失联，则恢复流程把该槽位改为 `needs_retry`，只允许用户显式重试。

这优先保证不因不确定的网络调用重复计费。依赖 Provider 支持上游幂等重放来自动恢复会锁死首个 Provider 实现，因此不作为 3B 的正确性前提。

### 5. 取消为队列边界的协作式动作

取消 API 把 `queued` 和 `leased` 槽位直接改为 `cancelled`；对 `dispatching` 槽位写入 `cancel_requested`。Worker 在写入生成资产前检查取消请求，命中时清理刚写入的对象并以取消完成，不向项目资产域发布结果。批次取消不删除已成功资产或尝试历史。

### 6. 前端以服务端批次状态替代浏览器生成运行态

`HeroImageWorkspace` 去除 3A 单张门禁。点击“编译提示词”后显示每个模块的确认卡与数量；确认后轮询批次读取接口，按模块和槽位显示排队、执行、成功、失败、取消和可重试状态。刷新只依赖服务端批次 ID 和状态，Zustand 只存恢复定位所需的非敏感 ID 与幂等键。

## Risks / Trade-offs

- [风险] 多个模块同时编译导致等待更长 -> 通过批次编译进度和每模块安全错误展示，未确认批次不触发生图。
- [风险] 数据库轮询造成额外负载 -> 通过小批量领取、指数退避空轮询和单用户默认并发 1 控制；事件推送留给后续阶段。
- [风险] Worker 崩溃后 Provider 已接受请求 -> 通过 `needs_retry` 显式人工决策避免重复计费。
- [风险] 取消与资产落库竞争 -> Worker 在资产发布前后检查取消状态，并复用项目资产删除补偿。
- [风险] 批量消耗更多额度 -> 确认界面明确显示模块数、总槽位数和将调用的次数，确认前不调用 Provider。

## Migration Plan

1. 添加新表、索引、状态约束和 Alembic 前向迁移；不改写阶段 3A 表。
2. 部署批次 API 和 Worker，但先保持 3A 页面入口不变；Worker 未启动时批次保留为排队状态且给出明确提示。
3. 将主图页面切换到批次确认和轮询视图，删除真实提交路径中的阶段 3A 单张门禁。
4. 回滚时先停止 Worker 和前端批次入口；已创建批次、尝试和生成资产保留用于审计，不对业务数据库执行 downgrade。
