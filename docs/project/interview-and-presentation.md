# PicAgent Studio：面试与项目讲解

整理日期：2026-10-09。内容按当前源码核对，包括未提交变更。技术能力可以据此讲述；个人负责范围、上线时间、业务收益和使用规模需要用本人真实经历补充。

## 1. 一句话定位

PicAgent Studio 是电商商品图片制作平台，将商品素材、内容规划、提示词编译、图片生成、编辑与成品归档组织成可追溯的工作流。

## 2. 一分钟介绍

> 我做的项目叫 PicAgent Studio，主要面向电商商品主图和详情套图制作。用户上传商品图并填写商品事实、平台和风格要求后，系统先规划每张图的内容与视觉方向，再编译提示词，经过用户确认调用图片模型，最后在画布上管理结果并继续编辑。
>
> 后端使用 FastAPI、PostgreSQL 和 MinIO，前端使用 React、TypeScript，以及 React Flow 和 Konva。规划模型通过 LangChain 接入兼容接口，批次图片生成由独立 Worker 执行。
>
> 我会重点介绍三个实现：常规版和专业版分别处理参数可控与整体设计需求；生成前冻结源图、配置和提示词，保证任务可追溯；批次拆成独立图片槽位，结合幂等、数据库租约和人工重试处理长耗时生成。

使用前将“我做的”替换成准确职责，如“我负责后端规划与任务执行”或“我主导前后端开发”。不要把整个项目功能自动等同于自己的职责。

## 3. 三到五分钟展开

### 3.1 业务问题

电商图片制作需要把商品事实转成卖点、模块、构图和文案。直接写一段自由提示词容易遗漏需求；多张图需要内容分工和视觉一致性，失败后也需要只重做其中一张。

因此项目采用“输入 → 规划 → 编译 → 确认 → 执行 → 编辑 → 归档”。规划决定每张图表达什么，编译展开画面描述，确认保存用户最终认可的文本，任务执行层负责模型调用和结果保存。

### 3.2 两种模式

常规版使用模块参数和本地规则编译，便于复用与人工控制；内容规划仍可以使用模型。专业版先做整套内容与视觉规划，再细化每张图，输出可交给图片模型的 `imagePrompt`。两者共享配置、素材和结果管理。

### 3.3 长任务管理

主图批次或套图确认后，系统为每张输出建立槽位。独立 Worker 从 PostgreSQL 领取任务，执行时续租，完成后保存图片及资产。前端查询服务端状态，页面刷新不会自动再提交生成。

### 3.4 修改与复用

用户可编辑最终提示词，也可通过对话提出规划修改。模型生成候选方案，用户应用后才成为新版本；修改过程中通过 revision 和输入快照识别过期结果。参考图反推保存为固定版本，复用视觉方法，同时保留当前商品事实边界。

### 3.5 当前边界

当前规划 Agent 没有工具列表，系统也没有在线训练、反馈自动学习或自建多 Agent Supervisor。业务身份还是本地单用户提供者。这样的边界说明能让实现讲述与源码一致。

## 4. 技术栈讲法

| 技术 | 建议说明的职责 | 不宜混淆的点 |
| --- | --- | --- |
| FastAPI + Pydantic | HTTP 接口、输入输出校验、业务错误契约 | 异步框架不自动解决后台任务持久化 |
| PostgreSQL + SQLAlchemy Async + asyncpg | 业务状态、任务、版本和关系持久化 | 文件内容主要放 MinIO |
| MinIO | 商品源图、生成图片和编辑结果 | 不是向量数据库 |
| LangChain + ChatOpenAI | 多模态整体规划的 Agent 运行入口 | `tools=[]`，不具备自主工具调用 |
| HTTPX + 兼容接口 | 单图编译、图像调用和错误适配 | 不是所有模型调用都经过同一个 Agent |
| 独立 Worker + asyncio | 批次槽位执行、续租和并发 | 当前不是 Celery、Redis 或 Kafka 队列 |
| React + TypeScript + Zustand | 工作台交互、草稿与会话状态 | 服务端任务状态仍是执行依据 |
| React Flow + Dagre | 生成关系的画布和布局 | 不负责后端工作流执行 |
| Konva + Pillow | 编辑交互与服务端图像处理 | 模型编辑和本地图像处理要分开解释 |
| Docker Compose + Nginx + Drone | 服务构建、代理与部署配置 | 当前流水线不自动迁移，也不证明测试或监控完整 |

具体规划模型与图片模型可配置，不应把某个示例模型名称说成唯一绑定。依赖清单的范围也不等于生产实际安装版本。

## 5. 可重点讲的技术亮点

### 5.1 两级规划把大任务拆成可确认的小任务

整套规划负责内容分工、模块顺序与视觉方向，单图细化负责具体画面。这样用户可以先审查任务书，再审查单图提示词；出现问题时也能定位是整体策略还是单图描述。

源码依据：`application/module_planning_service.py`、`module_planning_v2.py`、`providers/planning_agent.py`。

### 5.2 快照与版本让生成依据可追溯

任务保存源图哈希、配置与提示词版本、模型连接及最终文本。后续修改商城默认版本不会自动改变历史任务；需要采用新设计时重新规划或编译。

“冻结输入”能说明请求依据，但不能保证模型每次返回同样图片。模型服务行为、随机性与外部状态仍会影响输出。

源码依据：编译 service、`batch_generation_confirmation_service.py`、`suite_planning_confirmation_service.py`。

### 5.3 单图槽位和租约处理长耗时任务

每张图独立记录状态和执行尝试，批次汇总结果。Worker 使用数据库行锁领取槽位，并用租约 token 限制结果写入。未发送就中断的任务可以恢复排队，已经发送但结果不明的任务进入 `needs_retry`。

这是一种处理不确定结果的取舍，重点是避免盲目自动重复收费，不应表述为实现了外部调用严格 exactly-once。

源码依据：`batch_generation_repository.py`、`application/batch_generation_worker.py`。

### 5.4 对话修改使用候选方案与显式应用

模型通过有限的修改操作调整方案，先生成差异预览，应用后保存版本。输入改变时标记过期结果，避免模型旧回答覆盖新的手动操作。

源码依据：`planning_conversation_service.py`、`planning_conversation_patch.py`、`planning_conversation_models.py`。

### 5.5 参考方案复用保留商品事实边界

参考图反推形成整套视觉策略与逐图模块，可固定版本绑定到业务项目。当前商品的规格、文案和功能仍由当前输入提供，不能搬用参考商品事实。

源码依据：`reverse_project_service.py`、`reverse_execution_service.py`、`reference_content_policy.py`。

## 6. 常见追问与参考回答

### 6.1 为什么同时保留常规版和专业版？

常规版适合明确模块和参数的需求，编译规则较可控；专业版适合整体结构和视觉关系更复杂的需求，需要先规划再细化。两种方式共享生成执行和资产管理，用户可以根据任务选择，而不必每张图都走复杂规划。

### 6.2 你这里的 Agent 到底做了什么？

整体规划通过 LangChain `create_agent` 和 `ChatOpenAI` 执行多模态请求。服务端把业务 Skill、源图、事实、模块目录和输出要求放进上下文，模型输出 JSON 后由业务层校验。目前工具列表为空，业务流程仍由应用服务编排；我会把它称为有业务知识约束的规划 Agent。

### 6.3 Skill、RAG 和微调有什么区别？你用了哪种？

当前 Skill 是项目内置的规划知识文本，服务端按主图或套图场景加载并注入提示词。RAG 需要从知识库检索相关内容再组织上下文，微调改变模型参数。当前这条规划链路没有实现向量检索或模型微调。

### 6.4 怎么保证模型返回结构正确？

兼容服务使用 JSON mode，然后通过 Pydantic 和业务校验检查字段与引用。整体规划最多再进行一次纠正调用，SDK 关闭自动重试，避免预算失控。格式校验能保证结构可用，无法单独保证事实和审美正确，所以保留用户确认和商品事实限制。

### 6.5 为什么要编译后再确认？

规划文本和最终图片提示词不是同一层内容。确认阶段让用户检查实际会发送给图片模型的文本，并将当前文本、哈希和输入保存下来。当前实现支持用户改写提示词，最终 `finalPrompt` 使用确认文本，不再悄悄补回旧模板。

### 6.6 用户连续点击生成，怎么处理重复请求？

确认入口要求幂等键，并保存请求指纹。相同键和相同输入重放已有结果；相同键绑定不同输入返回冲突。套图确认还检查规划 revision，避免确认过期方案。前端恢复任务只查询已有 ID，不自动重新生成。

### 6.7 Worker 崩溃后怎么办？

数据库保存槽位状态及租约。未发出请求的 `leased` 槽位过期后重新排队；已经进入 `dispatching` 的槽位过期后标记 `needs_retry`，因为系统无法确认上游是否已经生成或计费。新 Worker 恢复扫描后继续处理可执行任务。

### 6.8 怎么避免多个 Worker 执行同一张图？

领取时使用 `FOR UPDATE ... SKIP LOCKED` 和状态更新，同一槽位由一个执行者取得有效租约。后续更新带 lease token，旧执行者不能随意覆盖新状态。但数据库保护与上游收费去重不是同一件事，仍需处理已经发送但本地没有结果的情况。

### 6.9 取消任务能立即停掉上游生成吗？

系统可以取消未执行槽位，对已发送请求记录取消意图。是否立即停止生成或退回费用取决于上游协议，不能保证。产品上要把本地停止接收后续结果与上游真正终止区分开。

### 6.10 并发是怎么控制的？

Worker 按配置限制进程内同时执行数量，滚动执行在有空闲位置时补领任务，并根据成功或失败调整当前并发。多个 Worker 的总并发不是自动共享同一个上限；扩容时需要额外设计全局限流和 Provider 配额管理。

### 6.11 页面刷新后为什么还能继续显示进度？

生成任务在服务端持久化，前端保存会话或批次标识并恢复查询。`useTaskRecovery` 在未完成时轮询，页面卸载只停止查询，不取消任务，也不重新发起生成。

### 6.12 怎么处理对话修改与手动修改的冲突？

提交反馈时冻结当前输入和方案。模型产生有限的修改操作，服务端校验后形成候选方案；用户确认应用才生效。revision 和上下文指纹用于识别过期结果，应用时合并候选和当前手动输入，并校验候选是否仍有效。

### 6.13 为什么使用 PostgreSQL 保存任务，而不是 Celery？

当前项目的批次、槽位、版本和资产关系本来就在数据库中，使用数据库队列可以将业务状态和任务状态集中管理，减少额外基础设施。代价是需要自己维护领取、租约、恢复和并发逻辑。任务规模或执行种类进一步增加时，可以评估引入成熟队列，但不能把这个改进说成已经实现。

### 6.14 为什么图片放 MinIO，元信息放 PostgreSQL？

图片是大体积二进制资源，对象存储更适合保存和访问；数据库适合保存项目归属、尺寸、哈希、版本和生成关系。完整恢复需要备份两边及模型连接加密密钥，不能只备份业务表。

### 6.15 生产部署有什么容易出错的地方？

API 和 Worker 要连接相同基础设施；只启动 API 会导致已确认批次停在队列。前端容器通过宿主机网关访问 API，Linux 下只绑回环可能出现 502。Nginx 配置修改要重新构建。当前 Drone 没有自动迁移，Schema 变更要单独执行。

### 6.16 你怎么测试这个系统？

后端用 Pytest 验证规划协议、人工提示词、幂等、租约、恢复和版本操作；Provider 可注入替身，避免测试依赖真实收费接口。前端用 tsx/node:test 验证业务辅助逻辑，用 Playwright 覆盖工作台与编辑流程，并执行 TypeScript 检查。真实模型效果需要单独评估，不能由这些自动化测试替代。

## 7. 容易讲过头的说法

| 不准确的表述 | 建议口径 |
| --- | --- |
| 自主多 Agent 协同执行整个项目 | 应用服务组织两级规划，整体规划 Agent 当前没有工具调用 |
| 接入 RAG 和向量数据库 | 使用项目内置 Skill 与设计知识，没有核对到该链路的向量检索 |
| 用户反馈会自动训练模型 | 对话反馈修改当前方案并保存版本；学习闭环是后续方向 |
| 所有后台任务都由同一独立队列可靠执行 | 批次生图有独立 Worker；对话反馈、编辑等入口有其他执行方式 |
| 常规版完全不调用模型 | 常规版编译走本地规则，内容规划仍可调用模型 |
| 最终提示词永远是原始 imagePrompt | 用户确认文本可覆盖编译文本，最终发送 finalPrompt |
| 已实现多租户认证与权限平台 | 当前采用本地单用户身份，存在工作区范围约束 |
| 严格保证不重复计费或图片完全一致 | 对不确定请求采用 needs_retry，保存依据但不保证上游 exactly-once |
| Langfuse、Prometheus 已全链路上线 | 依赖与配置存在；当前核对到日志、请求 ID、心跳及耗时记录 |
| 自动化流水线完成测试、迁移和上线 | 当前 Drone 配置主要执行检出、构建和启动，迁移单独处理 |
